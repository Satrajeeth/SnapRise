  # OTP Email Orchestration Framework (Standalone, Pluggable, Cost-Optimized)

  ## Summary

  Build a standalone FastAPI OTP service that:

  1. Sends OTP via multiple free email providers first.
  2. Uses weighted round-robin across eligible free providers.
  3. Automatically falls back to configured fallback providers.
  4. If all providers are unavailable, returns 202 Accepted and queues retries.
  5. Supports unlimited provider adapters (free and fallback) via a plugin-style interface.

  Service exposure will be internal-only private network, backend-to-backend access only.

  ## Public APIs / Interfaces

  ### HTTP APIs (internal)

  1. POST /v1/otp/send

  - Request: email, purpose (email_verification|password_reset), tenant_id, optional idempotency_key, optional locale
  - Response:
      - 200 when sent immediately: {request_id, status:"sent", provider_id}
      - 202 when queued due to outage/deferred retry: {request_id, status:"queued"}
      - 429 when rate-limited/backoff active

  2. POST /v1/otp/verify

  - Request: email, purpose, code, tenant_id
  - Response: 200 valid, 400 invalid/expired, 429 locked

  3. POST /v1/otp/resend

  - Same shape as send; enforces resend cooldown/backoff.

  ### Provider Adapter Contract

  Create a base interface each provider must implement:

  1. send_email_otp(payload) -> ProviderSendResult
  2. check_health() -> HealthResult
  3. classify_error(error) -> retryable | non_retryable | quota_exhausted | auth_error
  4. provider_metadata() (name, tier=free|fallback, weights, configured quotas)

  No code changes required to add providers beyond registering adapter + config.

  ## Architecture and Data Flow

  ### Core Components

  1. OtpAPI (FastAPI routes)
  2. OtpService (OTP generation, hashing, verification, attempt logic)
  3. RoutingEngine (provider eligibility + weighted selection + failover)
  4. ProviderRegistry (dynamic adapter registration)
  5. QuotaManager (configured limits + runtime counters)
  6. RetryDispatcher (queue producer/consumer)
  7. AuditLogger (events + provider attempts)

  ### Send Flow

  1. Validate request and rate limits.
  2. Generate OTP (6-digit), hash with per-record salt.
  3. Persist OTP challenge metadata.
  4. Route send:

  - Choose from healthy, quota-eligible free providers using weighted round-robin.
  - On retryable/provider failure, continue to next eligible provider.
  - If free providers unavailable/exhausted, try fallback providers (also weighted).

  5. If all fail:

  - enqueue retry job,
  - return 202 queued.

  6. Record attempt and provider telemetry.

  ### Verify Flow

  1. Fetch active challenge by (email, purpose, tenant_id).
  2. Enforce attempt/backoff policy:

  - after 1st failure: 30s lock
  - 2nd failure: 60s
  - 3rd: 120s
  - 4th: 240s
  - 5th: block challenge (max attempts reached)

  3. Compare hashed OTP.
  4. Mark verified and emit audit event.

  ## Storage Design

  ### Postgres Tables

  1. otp_challenges

  - id, tenant_id, email, purpose, otp_hash, salt, expires_at, status, attempt_count, next_allowed_at, created_at,
    verified_at

  2. otp_delivery_attempts

  - id, challenge_id, provider_id, tier, result, error_type, latency_ms, created_at

  3. provider_config

  - provider_id, tier, enabled, weight, priority, daily_limit, monthly_limit, settings_json

  4. otp_retry_jobs (or use external queue + job table)

  ### Redis Keys

  1. OTP throttles/cooldowns: otp:cooldown:{tenant}:{purpose}:{email}
  2. Provider runtime counters:

  - quota:daily:{provider}:{yyyy-mm-dd}
  - quota:monthly:{provider}:{yyyy-mm}

  3. Short-term idempotency cache: otp:idem:{tenant}:{idempotency_key}

  ## Reliability and Failover Policy

  1. Free providers used first by weighted round-robin among healthy + under-limit set.
  2. Automatic spillover to fallback group.
  3. Full outage behavior: enqueue retry + return 202.
  4. Circuit breaker per provider:

  - open on repeated failures,
  - half-open probe,
  - close on recovery.

  5. Background health checker updates eligibility.

  ## Security and Access

  1. Endpoint exposure restricted to private network only.
  2. Backend-only callers (no public client access).
  3. No end-user auth accepted at OTP service boundary.
  4. OTP never stored plaintext; hashed only.
  5. Structured audit logs for sends/verifications/failures.
  6. PII-safe logging (mask email in logs).

  ## Config Model

  Use env/config file + DB-backed provider rows:

  1. OTP_CODE_LENGTH=6
  2. OTP_TTL_SECONDS=600
  3. OTP_MAX_ATTEMPTS=5
  4. OTP_BACKOFF_SECONDS=30,60,120,240
  5. Provider registry list with unlimited entries.
  6. Queue settings (broker URL, retries, backoff strategy).

  ## Testing Plan

  ### Unit Tests

  1. OTP generation/hash/verify lifecycle.
  2. Backoff and lockout schedule.
  3. Weighted provider selection correctness.
  4. Quota exhaustion transitions free -> free -> fallback.
  5. Error classification and retryability mapping.
  6. Circuit breaker state transitions.

  ### Integration Tests

  1. Send succeeds on first free provider.
  2. First provider fails, second free succeeds.
  3. All free exhausted, fallback succeeds.
  4. All providers fail -> response 202 + queued job exists.
  5. Retry worker eventually sends after provider recovers.
  6. Verify success, invalid code, expired code, max-attempt lock.

  ### Non-Functional

  1. Load test send throughput with concurrent requests.
  2. Chaos test provider outages and recovery.
  3. Validate no plaintext OTP leakage in logs/DB.

  ## Rollout Plan

  1. Phase 1: one free provider + one fallback in production shadow mode.
  2. Phase 2: enable weighted multi-free routing.
  3. Phase 3: enable retry queue and circuit breakers.
  4. Phase 4: add provider onboarding playbook/template.

  ## Assumptions and Defaults

  1. Service remains internal-only in a trusted private network.
  2. Caller identity is controlled by network boundary and backend deployment controls.
  3. OTP use-cases in v1 are only email_verification and password_reset.
  4. Provider quotas are configured by ops and tracked via runtime counters (not provider usage APIs).
  5. Unlimited number of free/fallback providers supported via adapter registration.
  6. Full provider outage does not hard-fail request; it queues and returns 202.
